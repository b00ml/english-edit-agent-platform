## 1. 先确定这条链路交付什么

一个生成item交付的是结构化题目/语篇及其来源、自动QC结果，而不是一份已被专家认证的成品。正常路径最终落`pending_qc`；人工通过才是`passed`，发布才是`published`。

当前支持单选、完形、阅读三种内置题型，模板version3，均要求有效知识来源和人工核验。全局RAG_MODE仍optional，但模板required优先。灰区interrupt与“所有来源必须人工核验”不同：当前模板未开启灰区配置，自动达标内容照样需要后续人工审核。

本文负责生成/质量机制。任务投递及跨进程恢复见[04-任务执行与可靠性](04-任务执行与可靠性.md)；表关系与状态一致性见[03-数据模型与状态机](03-数据模型与状态机.md)；RAG证据如何得到见[02-文档处理与RAG](02-文档处理与RAG.md)。

## 2. 从页面参数到生成item：输入契约

### 2.1 当前请求字段

| 字段 | 含义 | 代码检查 |
|---|---|---|
| template_id | 数据库题型type_id | 存在、启用、可访问 |
| params.knowledge_point | 目标知识点，当前也用作检索query | 模板required字符串；来源无效时后续拒绝 |
| params.difficulty | 易 / 中 / 难 | 模板enum，并影响模型档案选择 |
| quantity | 总执行item数，1～50 | 请求Schema范围，用于worker拆分 |
| params.quantity | 渲染到单item Prompt的数量 | OPT-074已归一每执行项1 |
| params.topic | 阅读题可选主题 | 模板声明；缺省变量的渲染需注意 |
| tenant_id | 记录归属 | 服务端使用用户tenant，不接受任意外部伪造 |

示意请求（会真实产生任务和费用；只是解释，不是本轮执行）：

```json
{
  "template_id": "single_choice",
  "quantity": 2,
  "params": {"knowledge_point": "名词", "difficulty": "中", "quantity": 1}
}
```

这里外层2是两个独立item，内层1是每次生成一题。完形/阅读一个item是一篇，内部多个空/小题不是Celery独立item。

### 2.2 数量口径现已统一（OPT-074）

外层quantity为总批次N，内层params.quantity为每item1。GeneratePage先取总数再写内层1，service保存前同样归一；worker/Graph为历史task/checkpoint兜底，旧记录本身不批量改写。去重指纹包含batch quantity，防止不同批次总数被归一后误判相同。

多元素数组或多个对象包装不得静默取第一项；只有单字段单对象/单元素包装可展平，非法多输出进入Schema失败/反馈重试。实际页面5/8/2请求被拦截核对，真实PG五单项流程（模型mock）验证数量与重复消费；没有用真实provider输出50项认证质量。

原OPT-073“外层2/内层1”仍是当时手工请求范围，OPT-074才覆盖网页/API/worker数量契约。源码入口保持GeneratePage、GenerationService、worker/tasks和graph。

## 3. 配置对象与版本怎样协作

### 3.1 模板、Prompt和Skill

| 对象 | 决定什么 | 不能代替什么 |
|---|---|---|
| templates/*.yaml | input/output Schema、QC维度、模型档案、重试/改版/RAG策略 | 不包含全部自然语言出题规则 |
| prompts/*-system.st | 系统角色/规则/格式指令 | 不是服务端校验器 |
| prompts/*-user.st | 知识点/难度/数量/主题输入 | 不能承担权限/secret保护 |
| skills/<type_id>/SKILL.md | 题型专属命题规范 | 不会自动执行里面的文字为程序流程 |
| skill.meta.yml | 技能配套说明/版本资料 | 不能把文件存在等价运行时读取所有字段 |
| question_template | 活动配置副本、hash/version | 不保证旧文件内容一直可用 |

启动[template_loader.py](../../backend/app/template_loader.py)将YAML upsert入库；只改数据库模板可能被下一启动覆盖。[skill_registry.py](../../backend/app/skill_registry.py)实际按type_id读取同名SKILL.md，缺失回退generate_question；使用lru_cache，修改文件后需确保进程缓存刷新/重启。Judge用独立技能读取路径。

[prompt_loader.py](../../backend/app/prompt_loader.py)是简单`{{变量}}`替换，不是具有表达式/严格未定义变量检测的模板引擎；缺失变量会原样保留。新增可选topic等变量时应检查最终文本是否仍包含未展开占位符。

生成Prompt组成：system.st＋Skill＋输出Schema指令；user.st＋RAG参考文本＋可选改版指令。参考文本与业务字段分开构造，但最后都进入一次模型messages。不可把输入资料当作可信系统指令；现有来源/权限/输出校验是代码门禁，仍需评估资料中提示注入的语义风险。

### 3.2 版本可追溯但不是自动历史执行环境

template/prompt/skill/model hash和任务version_snapshot用于知道“当时配置是什么”。运行工作流仍从活动模板和文件加载部分信息；只有hash不足以恢复文件历史。摘要依然默认截断；OPT-077为新chat保存受限加密的完整脱敏messages/应用响应，需保留独立key且受预算/TTL约束。旧调用不能补造全文，源码/依赖/hash身份和模型非确定性仍是复现边界。

不要把“有version=2、trace_id”写成“任意旧任务可逐字原样重算”。详细持久化边界见[03-数据模型与状态机](03-数据模型与状态机.md)。

## 4. 模型路由与结构化输出

### 4.1 活动路由

- 单选：默认lite，难题standard；完形/阅读：默认standard，难题high。
- 当前三个DB档案实际均`deepseek-v4-flash`，不同档位强制检查关闭。
- Judge：ModelRoute.judge_profile覆盖→模板judge_model→JUDGE_MODEL_NAME→LLM_MODEL_NAME；本次只读快照主库route0，当前仍与生成同模型，未自动替换或宣称真实独立Judge增益。
- 模型档案具备enabled/冷却/失败计数/有限fallback和估算预算等状态；`MODEL_BUDGET_PER_TASK=0`未启用全局额度。

OPT-076管理员[/model-settings](../../frontend/src/pages/ModelSettingsPage.tsx)可自定义OpenAI兼容Provider、加密Key、模型标识和按题型生成/Judge档案。ModelRoute生成覆盖优先于原YAML难度分档，留空恢复原分档；未绑定Provider者ENV兼容，已绑定者实际使用其端点/密钥且不可暗中换成ENV。Provider/route持久化独立于模板启动同步，默认档案按scope SQL唯一。每次调用/QC快照保存安全档案/Provider配置身份，不记录密钥；费用仍后端单价估算。详细操作/限制见[第二轮与模型设置验收](../现状文档/10-6优化第二轮与模型设置落地验收.md)。

[router.py](../../backend/app/engine/router.py)先解析档案，生成失败后可尝试默认档案；默认与主档案相同模型时不是独立供应商容灾。修改模型要改活动DB映射而不只改环境默认，核对[model_governance.py](../../backend/app/model_governance.py)的引用检查。

### 4.2 配置候选的对比入口

[model_compare.py](../../backend/scripts/model_compare.py)默认plan-only；显式execute才调用已配置候选。每case共享冻结RAG/示例输入、交替候选顺序、无默认降级，保留失败、usage、估算费用和共享来源成本；输出不进入内容库，人工结论pending。当前lite/high仍同实际模型，门禁阻止无意义重复收费比较。三请求输入与10未标注候选已备于私有证据；不能据工具可用宣称不同模型/专家效果已验。

### 4.3 服务端结构校验

[structured_output.py](../../backend/app/engine/structured_output.py)：

1. 按output_schema构造动态Pydantic模型；
2. 通过JSON模式调用兼容API；
3. JSON解析，并对有限包装形态进行展平；
4. 原始归一结构先过JSON Schema以拒绝可被类型转换掩盖的非法输出，再经Pydantic二次校验；
5. JSON Schema检查嵌套字段等完整约束，再执行run_config.content_validation配置驱动跨字段规则；
6. 失败记录Trace和usage，向后续尝试提供校验反馈；
7. 达到max_retry后抛明确异常。

OPT-077每个chat应用尝试可保存完整脱敏messages＋收到的响应文本，独立加密/配额/TTL/权限审计；Trace摘要仍截断，旧调用不可补造，模型重跑不保证相同。受限快照与few-shot具体协议见[第三轮验收](../现状文档/10-6优化第三轮落地与验收.md)。

这是SDK＋校验重试，不是本地模型token级约束解码。嵌套Pydantic边界部分可用动态类型，完整JSON Schema兜底很重要，不能去掉其中一层。

OPT-075三种内置模板均升级v3：每选择小题恰好四个非空、不重复的选项正文，答案A/B/C/D映射数组位置；完形blanks非空、index从1按序连续且不重复，passage中____数与blanks一致。options不带字母标签；不静默重排/转换旧题。quantity为篇数，绝不是空格数。

[content_validation.py](../../backend/app/engine/content_validation.py)以配置路径声明根对象/小题数组、选项/答案/索引/空格字段，不按题型名称硬编码。Graph validate完整复查，失败按max_revise有界改版并回注错误，耗尽reject；QC缓存、store、submit_review和直接人工恢复不能绕过规则。至少5小题答案全部同位置仅warning，短批次不强制平均。

ContentItem.validation_report与payload/RAG provenance分开，QC快照与Trace也保存诊断；内容列表/详情只读返回现役规则诊断，不改历史分数和状态。前端显示结构错误/位置告警，确定性错误禁通过/发布，仍可驳回。格式合格不证明语义正确/唯一；完整实现与验收见[第四点验收](../现状文档/10-6优化第四点落地与验收.md)。

### 4.4 四种失败不能混算

| 失败 | 处理层 | 保留证据 |
|---|---|---|
| JSON/Schema不合法 | structured_output有限重试 | attempt、错误摘要、usage/成本 |
| 模型/HTTP瞬态异常 | 路由/worker分类与有限重试 | 结构化异常链、failure_code |
| 内容QC低分 | 工作流改版 | 上稿、维度分、revision、阈值 |
| 无有效required来源 | RAG/工作流chat前失败 | RAG状态、RAG_CONTEXT_REQUIRED；无生成chat |

重试耗尽/重新派发可能再调用模型；不能把item.attempts当作所有模型attempt总数。后台可靠性见[04-任务执行与可靠性](04-任务执行与可靠性.md)。

## 5. 工作流逐节点契约

| 节点 | 输入 | 输出/写库 | 失败行为 |
|---|---|---|---|
| generate | 模板/params/RAG策略＋服务器人审示例选择 | draft、rag_provenance、fewshot_report | 来源拒绝、模型/输出错误上抛 |
| validate | draft/完整Schema/跨字段规则 | validated＋诊断，或invalid＋具体错误 | invalid经有界revise→generate；耗尽reject，不无界重生成；语义正确性仍需人工 |
| qc | draft、规则/校准、约束、thread/revision | score、维度、阈值、QC snapshot；QualityEvaluation | 无效Judge耗尽记录failed事件并抛错 |
| revise | 当前draft、QC反馈 | 改版上下文、revise_count | 后续重新走generate，不是直接编辑数据库题目 |
| store | 自动达标draft | ContentItem pending_qc、auto QualityRecord、final QC事件 | 已有thread内容可复用，事务/唯一约束兜底 |
| reject | 耗尽未达标draft/原因 | 失败/拒绝内容证据 | 不当作人工passed |
| submit_review | 灰区稿/评分 | awaiting_review内容、auto记录 | 不直接人工通过 |
| human_review | checkpoint、人工decision | manual记录、passed/rejected、来源核验快照 | 未确认来源拒绝通过 |

图与节点真源[graph.py](../../backend/app/workflow/graph.py)。`after_qc`先判断达标，再看灰区（需enabled）再改版/拒绝。来源核验required不等于gray_margin开启。

## 6. 自动QC如何计算

### 6.1 输入和输出

Judge Prompt接收待测payload、模板rubric和**input_schema声明的生成约束**。rag_context、secret、改版旧稿不混入这些约束；RAG provenance保存在质量snapshot，不等于Judge逐字核对了所有源材料。

输出`dimension_scores`必须维度完整、ID唯一、严格数值0～100且finite；缺维度不得默默删掉后重新归一化。当前每轮最多3次尝试，2轮都必须得到有效结果；不是一轮失败就只平均剩下一轮。

### 6.2 计算示例

各维度先跨有效采样轮取均值，再按生效权重计算：

```text
维度均分 d_i = mean(每轮对应维度分)
总分 = sum(d_i × w_i) / sum(w_i)
通过 = completed 且 score >= 该轮snapshot.threshold
```

例如两个维度均分80/90、权重0.4/0.6，结果86。非法权重、零总权重、异常阈值必须拒绝，不以0分掩盖provider失败。

生效权重/阈值可以被校准覆盖；不能用全局70倒推所有旧事件是否通过。[quality_metrics.py](../../backend/app/engine/quality_metrics.py)依据每条事件的threshold计算first/final pass rate。

### 6.3 为什么需要两种质量表

- `QualityEvaluation`：thread＋revise_count唯一的每轮draft结果，包含completed/failed、is_final、规则/阈值/RAG snapshot。
- `QualityRecord`：绑定已落库内容，auto或manual_review，保留评分和配置来源。

自动首过率用revision0的评价事件为分母，最终通过率用已finalize事件；只统计ContentItem中留下的高分稿会丢弃失败和改版，造成幸存者偏差。

## 7. 人工复核、发布与回流

### 7.1 普通待质检路径

[quality_service.py](../../backend/app/services/quality_service.py)核对权限、scope、状态后创建manual_review记录，人工通过分数按100、驳回按0保存；ContentItem.qc_score会被人工分覆盖。要看模型原分必须读取auto QualityRecord/QualityEvaluation，不能只看内容当前qc_score。

人工通过还须[content_guard.py](../../backend/app/services/content_guard.py)按现役模板确定性校验；历史高分/旧稿不豁免，缺模板失败关闭。要求来源核验时，pass=true还须reference_verified=true并有citations；将reviewer和引用snapshot入provenance。重复同一审核者/相同决定可复用原记录，终态不能随意反向裁决。

### 7.2 灰区interrupt路径

awaiting_review且有thread时通过`Command(resume=decision)`恢复human_review节点；恢复后也更新task item/父任务聚合。普通pending_qc人工审核不等同于这一checkpoint恢复流程，不应直接向不存在interrupt的thread发送resume。

### 7.3 发布与样本

[content_service.py](../../backend/app/services/content_service.py)只允许passed发布，且按现役模板重新执行确定性校验；历史passed也不能绕过。需要来源审核时还核对reference_review.verified。发布记录人/时间，不向第三方系统推送。

[sample_service.py](../../backend/app/services/sample_service.py)只接受passed/published内容；[sample_pool.py](../../backend/app/sample_pool.py)按item_id幂等沉淀、显式同步、筛选与JSONL导出。OPT-077已接入generation few-shot：purpose=fewshot且同tenant/题型/规范化知识点、实际manual_review/源仍通过/hash一致/当前规则和来源核验均通过，整例最多2个/8192额外字符，不切断示例、不把示例当RAG事实。样本页可显式切换用途，客户端不能伪造上下文；新输出逐字复制样本会被代码拒绝/有限重试。当前主库样本0，未真实注例或认证收益；purpose=sft也不代表已经训练模型。

校准需auto/manual配对、同tenant、满足样本/假通过门槛；样本不足仍可写“未改变默认权重”的记录。权重降低不保证判题一定变准，要在独立人工集上检验。

## 8. 当前真实证据与人工检查模板

OPT-073真实单选2、完形2、阅读2均成功存pending_qc，QC 87.70～91.75；1次阅读JSON错误后成功重试。无来源负例chat=0。完形存在正确项位置偏置/潜在多解，不能说6条已人工通过。

建议逐内容人工标注：

| 检查项 | 记录什么 |
|---|---|
| 答案 | 是否正确、是否唯一、预期答案及具体反例 |
| 选项 | 同质、合理、标签/答案表示一致、位置偏置 |
| 解析 | 是否足够、是否与答案矛盾、是否偷换概念 |
| 知识点/难度 | 实际覆盖及偏离原因 |
| 来源 | 真正支撑哪个规则，page/block/segment/hash |
| 语篇 | 完形每空衔接、阅读每题原文依据、字数/语言 |
| 最终决定 | 通过/驳回/待修改；复核人/时间 |

[gold_eval.py](../../backend/app/engine/gold_eval.py)已定义人工确认、payload hash、答案/歧义/难度等标注字段；[quality_gold.py](../../backend/scripts/quality_gold.py)可导出未标注候选并验证报告。导出不是自动专家打标，不能由模型伪造human_attested。 GoldCase reviewed状态要求两名不同人工及版本/有效阈值证据；标签或预期答案有争议时需独立第三人仲裁。这是离线金标标准，不是普通UI一次审核自动达成的双人认证。

## 9. 修改与验证清单

- 改Schema：补嵌套/缺字段/非法enum/边界数组测试，不接受只改Prompt。
- 改Prompt/Skill：核对最终占位符、hash和缓存；保留系统/用户文件分离。
- 改QC：补缺维度/非法值/轮数耗尽/校准阈值分支，检查事件分母。
