## 2. 本机部署由哪些资源组成

| 资源 | 用途 | 丢失影响 |
|---|---|---|
| frontend容器 | Nginx静态前端和/api代理 | 界面不可用；不等于业务数据丢失 |
| backend容器 | API、模板启动同步、迁移/健康 | 请求/审核受阻，worker状态仍需查 |
| generation worker | 队列celery，concurrency5 | 未ack重投与checkpoint恢复需核对 |
| ocr-worker | 队列ocr，concurrency1 | 页/索引/局部复核延期 |
| shared beat（ocr-scheduler） | 常驻生成maintenance＋OCR sweep | 未启动会失周期补偿；不再限定OCR profile |
| PostgreSQL16/pgvector | 业务事实、向量、checkpoint | 必须DB备份恢复，不能create_all替代 |
| Redis7 | broker/result，OPT-074命名卷+AOF everysec | 不保证零丢失，SQL bounded对账/备份仍必要 |
| 宿主机MinerU | 本地OCR推理，独立环境/权重 | Compose健康并不证明OCR模型可用 |
| 主库/卷/私有env/源码 | 持久性基线 | 不能只备份Git或只备份DB |

[docker-compose.yml](../../deploy/docker-compose.yml)定义OCR profile和命名卷。Langfuse可选，但当前未启动、sink为db；启用前还需配置和验证，不是默认可观测性所依赖的必需服务。

## 3. 配置真源与生效方式

### 3.1 顺序与不同对象

- [config.py](../../backend/app/config.py)定义类型/默认/校验，Settings在进程导入时构建。
- Compose插值取启动进程环境及所选.env，**只有compose明确传入的键**才进入容器。本机受限部署辅助脚本复用运行容器配置并加载deploy/.env；不能假设根.env/示例文件或所有键会自动生效。
- 模板run_config覆盖部分全局行为（例如全局optional但内置required）。
- DB ModelProfile优先模型档案映射，改环境默认不会覆盖已有档案。
- API启动加载YAML upsert模板，而不是永远以DB编辑为准。
- 前端catalog提供布局、context模式、Top-K等；不同进程默认不一致可导致OCR plan hash失效。

### 3.2 2026-10-06运行配置

| 组 | 本机值 | 维护含义 |
|---|---|---|
| 环境 | production | 是启动校验模式，不是安全审计证书 |
| checkpoint | postgres /不允许memory降级 | backend/worker跨进程可恢复 |
| 模型 | lite/standard/high同deepseek-v4-flash | 不把三个名字当实际三个模型 |
| Judge | 同生成默认，2轮/最多3次无效尝试 | 真实独立Judge尚未启用 |
| 模板 | 3种version3，required/人工核验、retry3/revise3/阈值70 | 无来源先拒绝；不能自动发布 |
| RAG | structure /relation /hybrid、候选30、Top5/可选8 | 新资料默认；legacy显式回退 |
| context | 32768字符，byte保护None | 不是模型token窗口 |
| query | exact范围/aliases扩展/rules规划/rerank off | query增加可增加embedding成本 |
| embedding | text-embedding-v3 /1024 | 变维度需Schema与资料重建 |
| OCR | mineru后台/500页任务、小预览限制3页 | 服务/本地权重需单独核对 |
| Trace | db /durability=true | sink故障依赖持久spool或失败关闭 |

不要文档存明文密码/Key/JWT。已有admin密码以DB为准；seed不会用配置口令覆盖它。账号曾因本机便利调整过，公网前需要安全整改，不能直接复用演示凭据。

## 4. 只读状态与启动操作

下列默认工作目录为`<仓库根目录>`，命令区分只读/有副作用：

```powershell
Set-Location <仓库根目录>

# 只读服务状态
docker compose --env-file .env `
  -f deploy\docker-compose.yml --profile ocr ps

# 只读backend关键依赖探针
Invoke-RestMethod http://localhost:8000/api/health/ready

# 只读近期日志；原文/secret不要直接公开粘贴
docker compose --env-file .env `
  -f deploy\docker-compose.yml logs --tail 100 worker

# 有副作用：会更新容器、执行迁移/模板启动同步；确认备份和兼容性再执行
docker compose --env-file .env `
  -f deploy\docker-compose.yml --profile ocr `
  up -d --build backend worker ocr-worker ocr-scheduler frontend
```

API/worker改源码需要build；仅改环境要重新创建进程读取新值。前端单独展示修复可以针对frontend构建，注意Compose依赖服务可能也被处理；必要时明确`--no-deps`且确认后端兼容。本轮没有执行这些启动命令。

本地OCR参考[start-local-ocr.ps1](../../deploy/start-local-ocr.ps1)，要求明确已存在运行目录，独立端口/鉴权；不会自动为API装torch/下载模型。原页预览渲染库与OCR模型推理依赖是两回事。

## 9. 指标怎么解读

| 指标 | 正确分母/范围 | 常见误读 |
|---|---|---|
| 自动首过 | revision0 QualityEvaluation的有效定义 | 只统计最后留下的高分content |
| 最终自动达标 | 已finalize的事件与各自threshold | 一律用70重判历史事件 |
| 人工驳回率 | 实际人工标注集合 | 未标注稿当通过，或6题当长期指标 |
| context_complete | gold相关来源/词项/表行在实际segments中 | pageHit或candidate ID就算答案正确 |
| 模型调用数 | 模型stage/attempt，而非Trace总行 | lifecycle也计付费调用 |
| token/金额 | reported usage＋配置价格，失败也计 | 无usage=确实免费、估算=实付 |
| 时延 | 检索/推理/队列等待分阶段、样本和p50/p95 | UI一次快就证明大批量稳定 |
| OCR CER | 明确锚点/抽样页 | 少数锚点等于整书事实准确率 |

RAG来源gold、内容人工gold、结构边界负例是不同数据集；固定版本/hash/范围，保持模型/预算/语料变化单列。不能为了通过改标注或少评分送达内容。

## 11. 常见维护场景的处置顺序

1. **登录失败**：查用户名/active/实际DB口令，seed不覆盖；用户明确要求才重置，不顺手修改角色/全用户。
2. **任务停滞**：先Outbox→队列→item→Graph checkpoint，区分pending/dispatched/running；不盲重提交。
3. **高分坏题**：人工驳回并保原auto快照，复核选项/答案/来源，再进入反例规则与gold。
4. **RAG缺证据**：scope→源解析→embedding输入→两lane→fusion→实际segments/预算；只提高Top-K不是算法根因修复。
5. **OCR失败**：本地服务/鉴权→页/租约/hash→queue/sweep；成功页不整批重识别。
6. **重建拒绝**：源/预览/配置/结构签名/expected_revision，一致后重新免费计划，不能绕过门禁。
7. **成本不符**：stage/attempt/usage/多轮Judge/spool/price，明确历史窗口与当前累计。
8. **恢复需求**：先备份并确认具体对象，再受控补偿；不down-v/清库/删证据。
