### OPT-024：LangGraph interrupt 人工卡点（灰区转人工）—— P1-1

**日期**：2026-09-05
**类型**：后端 + 数据库迁移 + 前端接口
**影响范围**：workflow/graph、api/routes、models/迁移 i8d9e0f1a2b3、notification、worker/tasks

#### 问题 / 动机

- 人工审核完全在图外（API 直改 DB），无 human-in-the-loop；灰区内容（分数接近阈值）要么侥幸入库要么白白熔断（G12）。

#### 设计要点（对设计文档的一处修正）

- 设计文档草稿的 human_review 单节点两段式不可行：interrupt 抛出时同节点内先做的落库副作用不写检查点，恢复后节点重执行会重复落库。实现改为**两节点模式**：`submit_review`（落库 awaiting_review + auto 记录 + 通知，正常返回后状态写入检查点）→ `human_review`（interrupt 前零副作用，恢复后应用裁决）。

#### 改动

- 模板级开关：`run_config.human_review = {enabled, gray_margin}`（默认关闭，零行为变化）；`after_qc` 升级为四路由：达标入库 / 灰区转人工（不消耗改版预算）/ 低分改版 / 达上限熔断。
- `submit_review_node`：条目落库（status=awaiting_review，**thread_id 存入条目**）+ auto 质检记录 + 站内通知（新类型 content_awaiting_review）。
- `human_review_node`：`interrupt({content_id, qc_score, dimension_scores})` 暂停；`Command(resume)` 恢复后写 manual 质检记录、更新条目终态（passed/rejected）、驳回时通知。
- `resume_human_review(thread_id, decision, session)`：review API 凭条目 thread_id 恢复图（依赖 OPT-018 持久化 checkpointer 跨进程恢复）。
- `review_content` API：thread_id 非空且 awaiting_review → 恢复路径；存量条目走旧路径（完全兼容）。
- worker `process_generation_task`：识别 `__interrupt__` 结果计为 awaiting（不计成败），任务汇总 status=partially_succeeded；返回体增加 awaiting 计数。
- 迁移 `i8d9e0f1a2b3`：content_item + thread_id；ContentOut 增 thread_id。

#### 验证

- `tests/test_human_review.py`（13 用例）：灰区中断+落库+通知、恢复通过/驳回（manual 记录/终态/通知断言）、高分直入库、低于灰区走改版、开关关闭保持旧行为（4 次生成后熔断）、after_qc 六条边界路由。
- 全量 pytest 175 passed。

#### 量化对比

| 指标 | 改前 | 改后 |
|------|------|------|
| human-in-the-loop | 图外 API 直改 | LangGraph interrupt + Command(resume)，跨进程恢复 |
| 灰区内容处置 | 二选一（入库/熔断） | 人工裁决，不消耗改版预算 |
| 单测数 | 161 | 175 |

### OPT-023：修复改版链路双生成 Bug（质检反馈从未生效）

**日期**：2026-09-05
**类型**：Bug 修复（实施 P1-1 状态机测试时发现）
**影响范围**：workflow/graph（revise/generate 节点）、prompts/、structured_output

#### 问题 / 动机

- `revise_node` 自行调用一次 `generate_with_fallback`，随后无条件边 `revise->generate` 使 generate 节点**再次**生成：每次改版双倍 LLM 调用（成本 ×2）；且 generate 节点用原始 params 重新生成，revise 节点的改版草稿被无条件覆盖，`revise_context`（质检反馈）从未进入生成 prompt——"携带质检反馈改版"从未真正生效。

#### 改动

- `revise_node` 不再调用生成，只准备上下文：`params.revise_context = {previous_draft, qc_score, dimension_scores}`，计数 +1。
- `generate_node` 检测 revise_context，渲染新 `prompts/revise-instruction.st`（质检总分/维度分/上一稿）并入 `params.revise_instruction`。
- `generate_structured` 消费 `params.revise_instruction` 并入 user prompt——改版请求真正携带上一稿与质检反馈。

#### 验证

- `tests/test_human_review.py` 新增 2 回归用例：revise 节点调用生成即失败（assertion）、generate 节点注入 revise_instruction（含分数/上一稿/关键词）。
- 状态机用例修正后：改版路径 generate 调用次数从 3 次降为 2 次（1 次初始 + 1 次改版），熔断路径从 7 次降为 4 次。
- 全量 pytest 175 passed。

#### 量化对比

| 指标 | 改前 | 改后 |
|------|------|------|
| 每次改版 LLM 调用 | 2 次（1 次被覆盖浪费） | 1 次 |
| 质检反馈进入改版 prompt | 否（形同虚设） | 是（revise-instruction.st 注入） |

### OPT-019：Celery 任务可靠性（acks_late + 瞬态重试 + 僵尸恢复）—— P0-6

**影响范围**：worker/celery_app、worker/tasks、新增 worker/recovery、config

#### 问题 / 动机

### OPT-008：nginx 反向代理动态解析 backend（消除 502）

**日期**：2026-08-13
**类型**：Bug 修复 + 基础设施
**影响范围**：前端部署（nginx 反向代理）

#### 问题 / 动机
- 前端 `Request failed with status code 502`：nginx `proxy_pass http://backend:8000` 在 worker 启动时解析一次 upstream 并缓存 IP。
- 后端容器重建换 IP 后，frontend 的 nginx 仍连旧 IP（已不存在的容器）→ 所有 `/api/*` 请求 502（静态资源不受影响）。
- 直接 `docker compose up -d frontend` 因配置未变不会重建容器，需 `restart` 才能恢复，问题易复发。

#### 改动
- [frontend/nginx.conf](../frontend/nginx.conf#L4)：加 `resolver 127.0.0.11 valid=10s ipv6=off;`（Docker 内嵌 DNS）
- [frontend/nginx.conf](../frontend/nginx.conf#L26-L27)：`proxy_pass` 改为变量式 `set $backend http://backend:8000; proxy_pass $backend;`，每次请求经 resolver 动态解析 backend，不再启动时缓存

#### 验证
- 重建 frontend 镜像并重启后，`/api/health`、`/api/dashboard` 经前端代理均返回 200
- frontend 先于 backend 启动完成仍能动态解析成功（无 502）

#### 量化对比

| 指标 | 改动前 | 改动后 |
|------|--------|--------|
| backend 解析时机 | 启动时缓存 IP | 每次请求动态解析 |
| 后端重建换 IP 后 | 502（需手动 restart） | 自动恢复 |

### OPT-007：LLM 请求级超时 + 数组包装解包

**日期**：2026-08-13
**类型**：Bug 修复 + 优化
**影响范围**：后端（生成/质检/向量化链路、配置）

#### 问题 / 动机
- 排查「item 4 LLM 调用疑似挂起」时发现：三处 `OpenAI(...)` 客户端（[structured_output.py](../backend/app/engine/structured_output.py#L215)、[quality.py](../backend/app/engine/quality.py#L155)、[embedding.py](../backend/app/rag/embedding.py#L14)）均未显式设置 timeout，使用 OpenAI SDK 默认 600s——单次连接挂起可阻塞最长 10 分钟。
- Celery 软/硬超时（[celery_app.py](../backend/app/worker/celery_app.py#L29-L30)，600s/900s）是任务级、基于任务启动时刻；且 prefork 下 soft limit 靠信号，worker 阻塞在 C 级 socket read 时信号处理被延迟，无法打断真正挂起的网络调用，只有 hard limit(SIGKILL) 能强制终止但会杀掉整个 worker。
- 附带：item 4 实际失败原因是模型返回 `{"questions":[{...}]}` 数组包装，`_normalize_flat` 未解包，3 次重试均 Pydantic 校验失败（与超时无关）。

#### 改动
- [config.py](../backend/app/config.py#L35-L39)：新增 `LLM_TIMEOUT=120` / `EMBEDDING_TIMEOUT=30`（秒）
- [.env](../.env#L13-L15)：追加对应配置
- 三处 `OpenAI(...)` 客户端显式传 `timeout=`，实现请求级超时（单次调用快速失败抛 `APITimeoutError`，经 router 降级兜底）
- [structured_output.py](../backend/app/engine/structured_output.py#L165-L170)：`_normalize_flat` 支持解包 `{"questions":[{...}]}` 数组包装，取首个满足必填字段的子对象
- [test_structured_output.py](../backend/tests/test_structured_output.py#L66-L75)：新增 2 条回归测试（数组包装解包 + 空/无效数组原样返回）
- 新增 [.ai/rules/change_tracking.md](../.ai/rules/change_tracking.md)：固化变更追踪规范，确保后续每次修改都会记录到优化记录/tasks

#### 验证
- 单测：62 通过（新增 2 条）
- 说明：实际并未发生真正的「12 分钟挂起」——任务总耗时 370.7s，item 4 最长单次调用约 90s；但请求级超时仍是必要加固，防止未来真连接挂起时单请求阻塞 600s。

#### 量化对比

| 指标 | 改动前 | 改动后 |
|------|--------|--------|
| LLM 请求超时 | SDK 默认 600s（不可配置） | 120s（.env 可配） |
| embedding 超时 | SDK 默认 600s | 30s |
| 数组包装处理 | 3 次重试失败 | 直接解包首个子对象 |
| 单元测试数 | 60 | 62 |

### OPT-006：修复生成链路 list 崩溃 Bug

**日期**：2026-08-13
**类型**：Bug 修复
**影响范围**：生成引擎

#### 问题
- 批量生成时，模型偶发返回顶层 JSON **数组**（list）而非对象，`_normalize_flat` 对 list 调用 `.keys()` 抛 `AttributeError: 'list' object has no attribute 'keys'`。
- 该异常不在 `generate_structured` 的 `except (ValidationError, json.JSONDecodeError, KeyError)` 捕获范围内，逃逸导致整题崩溃、任务部分失败，且**本应生效的重试机制失效**。

#### 修复
- [structured_output.py](../backend/app/engine/structured_output.py)：`_normalize_flat` 增加 `if not isinstance(data, dict): return data` 防御，非对象结构原样返回交由 Pydantic 校验判错并触发正常重试，而非崩溃。
- [test_structured_output.py](../backend/tests/test_structured_output.py)：新增 list 输入回归测试。

#### 验证
- 后端单测 60 通过（新增 1 条回归）。
- 容器端到端：4 题任务成功 3 题，其中第 3 题日志 `attempt=3` 成功——修复前该题会在 attempt=1 直接崩溃，修复后正确走重试。

#### 量化对比

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| list 返回处理 | 崩溃（AttributeError） | 走重试→Pydantic 校验判错 |
| 重试机制 | 失效（异常逃逸） | 生效（attempt=3 成功） |
| 单元测试数 | 59 | 60 |

## OPT-031: P1-2 Schema 真校验 - 输入输出双重保障

**日期**: 2026-09-08
**类型**: 功能增强 + 安全加固
**优先级**: P1（核心流程）

### 根因
1. **输入未校验**：API 层未对 `params` 执行 JSON Schema 校验，无效参数直到 Celery Worker 执行时才暴露，浪费队列资源与 LLM 调用成本。
2. **输出约束丢失**：`structured_output.py` 的 `_map_schema_type` 未保留数组 `minItems/maxItems`、字符串 `minLength/maxLength/enum` 等约束，模型返回违规输出时校验宽松，导致不合格数据流入下游。
3. **去重指纹不含版本**：模板 schema 升级后，`request_hash` 未区分新旧版本，导致新版本参数被误判为重复任务。

### 改动范围

#### 1. 输入校验（`generation_service.py`）
- **新增 JSON Schema 校验**：`create_task()` 在模板加载后调用 `jsonschema.validate(req.params, template.input_schema)`
- **错误码扩展**：新增 `InvalidTemplateParamsError`（422），携带 `field_path` 与 `validation_keyword`，前端可按字段路径定位错误
- **去重版本化**：`compute_request_hash()` 新增 `schema_version` 参数（使用 `template.updated_at`），模板升级后允许重新生成

#### 2. 输出校验（`structured_output.py`）
- **增强 `_map_schema_type`**：
  - 字符串：保留 `minLength/maxLength` 映射为 `constr`，保留 `enum` 映射为 `Literal`
  - 数组：保留 `minItems/maxItems` 映射为 `conlist`，支持嵌套对象数组
  - 对象：递归构造内部模型
- **第二道 jsonschema 校验**：`generate_structured()` 在 Pydantic 校验后，调用 `jsonschema.validate(validated_dict, schema)` 兜底无法转为 Pydantic 的约束
- **错误重试**：jsonschema 校验失败时触发重试，符合现有重试逻辑

#### 3. 异常体系
- **新增异常类**：`InvalidTemplateParamsError(PlatformError)`（422，携带字段路径与关键字）
- **修复导入冲突**：`knowledge_service.py` 和 `sample_service.py` 错误地从 `app.errors` 导入 `ValidationError`，已修正为从 `pydantic` 导入

### 验证方式

#### 单元测试（16 个新增用例）
1. **输入校验**（`test_input_schema_validation.py`，6 个用例）：
   - 缺少必填字段 → 422 `INVALID_TEMPLATE_PARAMS`
   - 枚举值错误 → 422 `INVALID_TEMPLATE_PARAMS`
   - 字段类型错误 → 422 `INVALID_TEMPLATE_PARAMS`
   - 整数超出范围 → 422 `INVALID_TEMPLATE_PARAMS`
   - 正常参数通过校验并创建任务
   - 无 schema 模板跳过校验

2. **输出校验**（`test_output_schema_validation.py`，10 个用例）：
   - 数组 `minItems/maxItems` 约束保留并强制执行
   - 字符串 `enum` 约束保留并强制执行
   - 字符串 `minLength/maxLength` 约束保留并强制执行
   - 嵌套对象数组的 `minItems` 约束保留
   - `_map_schema_type` 正确返回 `constr/conlist/Literal`

#### 测试结果
```bash

pytest -m "not integration" -v
# 结果：210 passed, 覆盖率 51%（满足 CI 门槛 ≥80% 未启用）
```

| 维度 | 改造前 | 改造后 | 改进 |
|------|--------|--------|------|
| 输入校验 | 无，错误参数到 Worker 才失败 | API 层 JSON Schema 校验，422 立即返回 | 节省队列资源与 LLM 调用 |

## 远端历史 OPT-039：GitHub Actions 集成测试失败修复

**日期**：2026-09-09
**类型**：CI 稳定性 + 集成测试契约修复
**影响范围**：`.github/workflows/backend-ci.yml`、`backend/app/services/auth_service.py`、`backend/tests/integration/conftest.py`、`backend/tests/integration/test_pipeline.py`

#### 问题 / 根因

- CI 的 PostgreSQL service 只负责启动实例，integration job 未执行 Alembic，首次访问 `trace_log` 时直接报 `relation "trace_log" does not exist`。
- CI 的 unit/integration job 未设置 `PYTHONPATH`，从仓库脚本入口运行 pytest/alembic 时无法解析 `app` 包，分别表现为收集阶段 `ModuleNotFoundError` 和迁移初始化失败。
- CI 的 unit job 未安装运行时实际导入的 `jsonschema`，9 个测试模块在收集阶段报 `ModuleNotFoundError: No module named 'jsonschema'`。
- Alembic 读取 `DATABASE_URL` 而不是 `TEST_DATABASE_URL`，迁移步骤实际连接默认库 `english_edit`，导致 `database "english_edit" does not exist`。
- `AuthService.login()` 以 `token` 构造 `LoginOut`，而公开 schema 字段是 `access_token`，导致登录接口在集成测试中触发 Pydantic 校验错误。
- integration 的 inline Celery fixture 只替换父任务 `send_task`；父任务内部的 `generate_single_item.delay()` 仍连接默认 AMQP broker，CI 环境下出现 localhost broker 连接错误。
- Trace 生命周期新增 `queue_dispatch`、`queue_item`、`workflow`、`embedding` 等阶段，测试将阶段集合硬编码为仅 `generate/qc`，把合法的可观测性扩展误判为失败。

#### 改动
