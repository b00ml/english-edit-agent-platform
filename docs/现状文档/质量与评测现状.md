## 结论摘要

当前项目已经建立了“结构合规 → 自动 Judge → 低分改版 → 人工审核 → 发布”的质量机制，足以支撑人工把关下的批量生产。它还没有建立能够证明英语题目事实正确、答案唯一、解析准确、知识点命中和难度稳定的独立评测闭环。

因此，当前最准确的表述是：

> **质量控制机制已实现，质量目标尚未被当前版本的独立数据证明。**

## 质量标准来自哪里

三类模板在 YAML 中声明 `quality_rules`，包含维度、权重、描述和 0–100 分档 rubric；模板加载器校验规则非空并校验权重和。生成 Prompt、Judge Prompt 和题型 Skill 独立存放，RAG 命中片段作为生成参考上下文。

| 题型 | 当前维度与权重 | 主要判断对象 |
|---|---|---|
| 单选 | `kp_match .30`、`diff_match .20`、`distractor .30`、`unambiguous .20` | 知识点/难度匹配、干扰项质量、唯一性 |
| 完形 | `context_coherence .30`、`option_validity .30`、`answer_correctness .25`、`difficulty_match .15` | 语境、选项、答案与解析、难度 |
| 阅读 | `passage_intelligibility .25`、`question_alignment .30`、`option_validity .25`、`answer_correctness .20` | 语篇、设问对齐、选项、答案与解析 |

这些 rubric 能约束 Judge 的评分尺度，但不构成可执行的事实核验规则。尤其是英语题目的“答案是否正确”和“是否存在多解”，不能仅靠同一个或相近模型的文本评分推断。

## 四层质量关口

| 层级 | 当前代码行为 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 输入约束 | `/api/generate` 按模板 `input_schema` 做 JSON Schema 校验 | 参数完整、枚举和数量范围合法 | 目标知识点是否值得出题 |
| 输出结构 | 动态 Pydantic + JSON Schema 二次校验 | 字段、类型、数组和部分长度/枚举约束 | 答案、解析、事实和唯一性正确 |
| 自动 Judge | 按 rubric 逐维打分，多轮可取均值，再按权重汇总 | 让低质量样本更容易被拦截，提供排序/改版反馈 | Judge 分数与教研员真值一致 |
| 人工审核 | `pending_qc` 经过人工通过/驳回，只有 `passed` 可发布 | 最终发布前有人承担内容责任 | 未被抽检样本的整体质量 |

## 当前质量路径

1. 结构化引擎向模型要求 JSON，输出先解析，再经 Pydantic 校验和 JSON Schema 校验。
2. 校验失败按模板 `max_retry` 重试，默认 3 次，并尝试把字段级错误回注 Prompt。
3. Judge 读取题型 rubric，对草稿返回维度分；代码按权重汇总为 0–100 分。
4. 分数达到当轮有效阈值（校准值优先，其次模板值）（现有模板默认 70）进入 `store`，保存为 `pending_qc` 并写一条 `QualityRecord(source=auto)`。
5. 低于阈值时，模板若启用灰区人工卡点且分数落入灰区，进入 `awaiting_review`；否则进入改版，默认最多 3 次。
6. 改版耗尽后写 `ContentItem.rejected`；人工通过写 `passed`，人工驳回写 `rejected`；发布只允许 `passed -> published`。

结构化重试和自动改版是两层不同预算：前者解决输出格式，后者解决质量评分不足。改版路径没有当前版本的实验数据证明一定改善质量。

## 本轮质量修复（2026-10-04）

1. Judge 用户 Prompt 现在独立注入模板声明的生成约束，不从草稿猜测目标知识点/难度；RAG、改版上下文和凭据不属于评分目标。
2. 评分使用动态 Pydantic 强校验：维度齐全、无未知维度、分数为 0–100 有限数，不接受 bool 或数字字符串。任何一轮失败会有限重试，耗尽明确失败，不对剩余维度归一化或用少量有效采样伪装全部成功。
3. Pydantic、JSON 和 JSON Schema 专属错误全部进入结构化反馈重试，失败 Trace 保留 token/成本，重试耗尽明确失败。
4. 新增 quality_evaluation，每个 thread/改版轮次一条结果（底层重试另在 Trace）；低分淘汰也保存最终 auto quality_record。统计按事件自身有效阈值，首轮与已终结最终轮使用不同分母，无样本返回 null。
5. 校准有效阈值同步到工作流路由、灰区、事件和快照；人工记录复用原 auto 快照。断点重放使用已冻结阈值，不把 0 当成缺省。

以上通过纯单测，不等于真实内容效果改善。新增事件表尚未在真实 PostgreSQL 迁移，历史数据不虚构回填首过/失败事件。

## 校准与数据回流的真实状态

`quality_calibration` 支持按人工通过/驳回配对样本计算维度“放水度”，下调容易高估的维度权重，并在后续 `qc_node` 使用覆盖权重。默认需要至少 20 个标注对和 5 个假阳性样本才会产生有效校准。

当前限制：

- P1 已按租户隔离校准数据与运行时覆盖，管理员可显式选择租户；模板版本/时间窗训练分层仍未完成，不把混用时期的校准效果作为证明。
- 本轮已统一校准有效阈值与路由/快照；仍未通过独立人工对照集证明校准实际收益。
- `sample_pool` 可以沉淀人工通过/已发布内容并导出 JSONL，但生成链路没有自动 few-shot 消费或训练作业；“数据回流已实现”不等于“生成质量已因回流提升”。

## 指标的正确读法

| 指标 | 当前口径 | 使用时必须补充的限制 |
|---|---|---|
| 结构化首过率 | 生成 thread 第一次 attempt 即成功 / 有生成 Trace 的 thread | 只看格式合规，不看语义正确 |
| 结构化最终失败率 | 没有成功生成 Trace 的 thread / 有生成 Trace 的 thread | 外部 API、路由和 worker 失败需结合生命周期 Trace |
| 自动首过率 | revise_count=0 的完整评分事件中达标 / 存在首轮事件的唯一 thread | 按每轮实际阈值；历史缺首轮事件不参与；不等于内容正确率 |
| 自动最终通过率 | 已终结最后评分事件中达标 / 已终结评分 thread | 运行中最后评分不作为最终结果；改版淘汰/Judge 耗尽都在分母；无样本 null |
| Judge 最终失败率 | 最终事件 status=failed / 已终结评分 thread | 不包括没有进入 qc 的结构生成失败，需结合 worker/Trace |
| 人工驳回率 | 人工记录中 `score=0` / 全部人工记录 | 只代表被审核集合，若人工只看疑难题会有选择偏差 |
| 改版触发率 | `revise_count >= 1` 的内容 / 全部内容条目 | 失败且没有内容条目的路径不在分母 |
| Judge/人工一致性 | 自动分数按阈值二值化，与人工 100/0 比较 | 是二值放行一致性，不是逐维质量真值；样本小于 30 只应视为提示样本不足 |

## 建议的最小评测方案

固定一个版本化评测集，至少按三类题型、易/中/难和主要知识点分层。每题由教研人员记录：答案是否正确、是否多解、解析是否正确、知识点是否命中、难度是否合适、判定依据和争议说明；争议题做二次复核。

每次版本评测必须冻结并记录：模板版本、Prompt/Skill hash、生成模型、Judge 模型、温度、阈值、RAG 是否启用、数据集版本、样本量和时间窗口。至少同时报告：

- 自动放行样本的答案/解析错误率；
- 人工驳回率及其样本量；
- Judge 与人工的假阳性/假阴性；
- 改版前后通过率和错误类型变化；
- 每题成本、延迟、重试次数和 RAG 命中率。

在拿到这些证据之前，面向使用者可以说“质量控制机制已建立”，不能说“自动质检稳定”或“人工驳回率已达标”。
