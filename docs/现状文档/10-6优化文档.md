**有。最紧急的不是继续优化 RAG，而是先处理“批量数量契约”和“任务投递、恢复闭环”。** 这两类直接影响你接下来批量生产时的费用、结果数量和任务是否能完成。

我刚重新检查了源码、调度配置以及 Redis 实际配置。下面是针对**个人自用、保留人工复核**这一使用方式的优先级，不把所有问题都一律定为 P0。

## 一、批量生产前优先解决的 3 项

### 1. 批次总数量与单次生成数量混用
**优先级：P0，第一项修。** 注释 1

当前真实路径是：

```text
网页选择生成 5 条
→ 请求 quantity=5，params.quantity也=5
→ worker拆成5个执行项
→ 每个执行项的Prompt仍要求生成5题/篇
→ 输出Schema却通常要求一个对象
```

我做了不调用模型的本地检查，确认：

- 单个执行项的 Prompt 会保留“5 道”；
- 模型若返回 `{"items": [5个对象]}`，当前包装展平逻辑可能只取第一个符合结构的对象。

**影响：**
- 模型可能生成了多份内容，却只保存一份；
- 输入指令与输出 Schema 冲突，增加重试和费用；
- 页面选择的数量与模型实际工作量不一致。

这**不等于已证明每次都会生成 25 题**，但数量契约冲突已明确存在，不能继续把网页多数量路径当作已验收。

**建议修法：**
- 批次总数只负责拆分任务；
- 每个执行项明确生成一题或一篇；
- 服务端统一执行项参数，不能仅靠前端修正；
- 补网页请求、API、worker、Prompt 和输出数量的回归。

**修复前：网页先使用数量 1。**

---

### 2. Outbox 与执行项投递缺少完整补偿
**优先级：P0，第二项修。** 注释 2

当前存在两个不同的缺口：

| 位置 | 实际问题 |
|---|---|
| API → 父任务 | 创建后尝试一次 Outbox relay；当前 beat 只有 OCR sweep，没有周期生成 relay |
| 父任务 → 子任务 | 先写入全部 item 和 `dispatched`，再逐个发送消息；中途失败可能留下部分未投递 item |

另外，死信重放目前只是：

```text
dead → pending
```

**并不会直接保证事件被重新发送。**

现有启动恢复主要查找超时的 `running` 父任务，不能完整覆盖：

- 一直 `pending` 的 Outbox；
- 已 `dispatched`，但部分 item 没收到消息的任务；
- Outbox 已 `sent`，但队列消息后来丢失的任务。

**影响：**
- 用户已经拿到 task_id，但任务可能长期不执行；
- 批次可能停在某个进度；
- 人工重复提交又可能增加混乱和费用。

**建议作为一个修复包完成：**
1. 配置周期生成 relay；
2. 加强 relay 的并发领取，避免多个消费者重复抢同一事件；
3. 为子任务投递建立可追踪的补偿机制；
4. 对超时未执行的 task/item 做有界对账；
5. 验证死信重放确实能走到执行完成；
6. 恢复时不重新执行已完成、已取消或等待人工的条目。

目前数据库里 Outbox 都是 `sent`，任务也没有活动积压；**这是可靠性缺口，不是当前已经出现大规模挂起事故。**

---

### 3. Redis 持久化与消息丢失恢复
**优先级：P0/P1边界，建议紧接投递闭环一起处理。**

这次实际配置核对比文档中的静态判断更明确：

- Redis `appendonly=no`；
- 有默认 RDB 快照配置；
- `/data` 当前挂载的是**匿名卷**，不是项目明确管理的命名卷。

因此不能说“Redis完全没有持久化”，但也不能说“队列消息已可靠持久保存”。

**影响：**
- RDB 快照之间的新消息可能丢失；
- 容器重新部署、卷处理不当时，消息保留行为难管理；
- 即使数据库中的 Outbox 已经 `sent`，队列消息丢失后也没有完整自动对账。

**建议：**
- 使用明确的命名卷；
- 配置合适的 AOF 策略；
- 保留数据库任务对账与补偿。

**不能只开启 AOF 就算修完。** 持久化降低丢消息概率，数据库对账负责处理仍可能发生的缺口。

## 二、下一批内容生产前应加强的质量问题

### 4. 自动高分仍可能出现错误或多解
**优先级：P1，但开始扩大内容生产前应处理。**

当前人工审核和发布门禁仍在，所以它还不是“坏题自动公开发布”的失控问题。但它会明显增加人工返工。

尤其完形 Schema 目前主要规定字段类型，没有充分强制：
- 每空恰好四个选项；
- 空序号连续且不重复；
- 题干空数与 `blanks` 数一致；
- 答案表示方式统一且能对应选项；
- 选项不为空、不重复。

建议分两层处理：

| 层次 | 做什么 |
|---|---|
| 确定性校验 | 用代码拒绝上述可判断错误，接入现有重试或改版路径 |
| 语义质量 | 对答案唯一性、连词潜在多解等建立人工反例与评测，不指望简单规则全部判对 |

正确选项全部集中在 A 可以先作为质量告警；**不要不加区分地把每个短批次都要求均匀分布，也不要静默打乱选项却忘记同步答案。**

换独立 Judge 可以后续比较，但不应成为跳过这些确定性校验和人工复核的理由。

## 三、可排在第二轮的问题

| 问题 | 建议优先级 | 原因 |
|---|---|---|
| task/item/Graph/前端状态命名不一致 | P1 | 修改恢复逻辑时容易判错终态；应与投递修复一起核对映射，而非仅做改名 |
| 请求去重的并发保护 | P1 | 当前是先查询再创建，`request_hash` 没有 SQL 唯一约束；并发请求可能绕过应用防重 |
| Trace 长文本截断 | P1/P2 | 影响完整问题复现，不直接造成任务丢失；应设计受限完整快照与摘要分离，不能直接关闭脱敏无限存储 |
| 三档模型实际相同、Judge也同模型 | P2 | 当前更多是效果、成本分档和容灾收益不足，不是必须马上换模型的程序错误 |
| 样本库尚未自动参与 few-shot | P2 | 是尚未连接的能力，不是当前主链路故障 |
| 42／45 条集成测试计数差异 | 文档问题 | 已说明统计更正，不需要为此修改业务逻辑 |

还有一处需要纠正先前主文档中的推断：**Repository 的去重查询实际只筛选活动任务状态**，所以并非所有已经结束的相同请求都会永久被拦截。真正要补的是并发防重，而不是简单取消去重。

## 推荐修复顺序

```text
第一批：
数量契约
→ Outbox与子任务投递补偿
→ Redis持久化及消息丢失对账
→ 对上述路径做故障回归

第二批：
题型确定性校验
→ 人工反例与质量评测
→ 状态映射一致性
→ 并发请求防重

第三批：
完整Trace快照
→ 独立Judge／模型档位实测
→ 样本few-shot回流
```

**我的建议：先完成第一批，再扩大网页批量生成。** 在此之前仍可单条生成、人工核验后使用；不要删除 legacy 回退，也不要关闭来源和人工发布门禁。

本轮只进行了源码、配置和不收费的本地逻辑复核，没有修改业务代码、重启服务或调用真实模型。
