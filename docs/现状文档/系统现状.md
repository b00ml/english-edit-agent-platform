## 先给结论

### 是否足以作为自用生产项目

**代码层面已具备受控自用生产基础，实际部署准入尚未完成。** 当前系统可以作为个人或小团队的受控内容生产工具，用于批量生成单选、完形和阅读题，经过自动质检、人工审核后再发布。它已经具备生产闭环所需的主要软件骨架，不再是只能演示单条调用的 Demo。

但这里的“生产”必须理解为：

- 单租户或可信的小团队使用；
- 生成结果默认进入人工审核，不把 Judge 分数视为事实正确性证明；
- 使用真实 PostgreSQL、Redis、LLM 和 embedding 服务，并在启动后检查就绪探针；
- 由操作者负责备份、死信/失败任务处理和质量抽检；
- 先按小批量使用，当前没有可引用的吞吐、并发或成本基准。

**不应据此宣称已经达到无人值守生产、对外 SaaS、多租户隔离或质量目标达标。** 本轮已补齐租户传递与非管理员 scope，但真实迁移、并发和多租户生产隔离未实测；全局 admin 仍可跨租户操作；`≤5%` 人工驳回率也没有当前版本的独立金标集证据。

| 使用场景 | 当前判断 | 依据与限制 |
|---|---|---|
| 个人自用、小团队批量出题 | **可用，但需人工把关** | 三类模板、批量 item、自动质检、人工审核、发布和成本/Trace 页面已实现；真实外部依赖和生产配置尚未在本次运行 |
| 有人工审核的内部生产 | **可作为候选生产系统** | 失败、取消、重试、Outbox、checkpoint、健康检查均有代码入口；跨进程恢复和真实部署需复验 |
| 无人工审核自动发布 | **不可接受** | Judge 只做 LLM 评分，不能证明答案正确、唯一解、知识点事实或解析准确 |
| 多用户、多租户共享服务 | **当前不建议** | 代码已建立非管理员资源 scope；admin 为全局管理员，真实迁移/隔离与并发验收仍待完成 |
| 对外商业化或高并发 | **未达到准入条件** | 没有当前吞吐/并发/压测数据；CORS、备份、告警、数据隔离和运维流程仍需加固 |

## 架构总览

```text
React 工作台（11 个登录后页面）
        │ REST + JWT
        ▼
FastAPI（45 个 API 路由）
        │
        ├─ Service / Repository：任务、内容、质检、知识、样本、认证
        ├─ PostgreSQL 16 + pgvector：业务表、Trace、知识向量、配置快照
        ├─ Redis：Celery broker/result backend
        └─ TaskOutbox：事务提交后的可靠投递
                │
                ▼
        Celery worker：批量拆 item、重试、取消、僵尸任务恢复
                │
                ▼
        LangGraph（每个 item 一个 thread_id）
        生成 → 结构校验 → Judge 质检 → 改版 loop / 人工卡点 → 入库 / 拒绝
                │
                ├─ engine：结构化输出、模型路由、Judge、Trace/成本
                └─ rag：资料解析、embedding、pgvector 检索
```

实际入口和边界：

- `backend/app/api/routes.py` 仍承载成本、看板、Trace 等复杂聚合查询；生成、内容、质检、知识等主要路径已拆到 `services/` 和 `repositories/`。
- `backend/app/workflow/graph.py` 直接使用数据库 Session，工作流和 API 并非完全通过 Repository 访问数据。
- 断点默认尝试使用 `PostgresSaver`；初始化失败时开发环境可降级为 `MemorySaver`；生产/staging 在 `ALLOW_MEMORY_CHECKPOINTER=false` 时禁止任务使用内存断点，ready 探针也会阻止放行。
- Trace 的事实源是自研 `trace_log`；Langfuse 是可选 Sink。写库失败可持久化到补偿卷并幂等重放；严格模式无任何持久化通道时失败关闭，有 process-local health/丢失告警。它仍不是业务事务日志或供应商账单。

### 生成、质检和发布闭环

单个 item 的当前主路径是：

1. 生成请求校验题型和参数，计算请求指纹；活跃的相同请求被拒绝。
2. 创建 `generation_task` 与 `task_outbox`，同一事务提交；relay 成功后投递 Celery。
3. dispatcher 按 `quantity` 创建 `generation_task_item`，每个 item 使用 `{task_id}:{item_index}` 作为 LangGraph `thread_id`。
4. `generate` 节点按知识点尝试 RAG，再走结构化生成和模型档案降级。
5. `validate` 做结构兜底，`qc` 调用 Judge 按 rubric 加权，低分进入改版 loop。
6. 达标内容保存为 `pending_qc`；低分且耗尽改版次数的内容保存为 `rejected`；灰区模板可以进入 `awaiting_review` 并用 checkpoint 等待人工裁决。
7. 人工通过后变为 `passed`，只有 `passed -> published` 可以发布。

当前可靠性机制包括：

- Celery item 级并发、late ack、基础设施异常自动重试；
- Outbox 稳定 `event_id` 和 Celery task id，失败次数耗尽进入 `dead`，提供 replay 脚本/接口；
- 运行中任务超时可在 worker 启动时重置并重投；
- item 终态跳过重复执行，LangGraph checkpoint 用于续跑；
- 任务取消采用合作式退出，当前没有独立的暂停/恢复 API；瞬态失败按结构化异常有限重试，耗尽更新父子终态；
- `/api/health/live`、`/api/health/ready`、`/api/health/dependencies` 提供进程和依赖探针。

### RAG、样本和可观测性

- 知识库统一经 KnowledgeService/indexer/retriever，同一租户读写、检索与删除；支持 txt/md/docx/pdf 解析、按字符分块、embedding、pgvector 余弦检索和知识点过滤。
- 生成前按 `knowledge_point` 检索默认最多 3 个片段，并把文本注入 user prompt。
- RAG 支持 off/optional/required：optional 降级继续但记录状态，required 无有效命中失败关闭。来源快照/hash 随内容与质量快照保存；配置来源必审时发布受人工核验门控。仍不自动证明事实正确。
- 样本池可沉淀人工通过/已发布内容、列表、删除和 JSONL 导出；生成链路没有自动 few-shot 消费或训练作业。新增 quality_gold.py 提供真实人工金标候选导出与离线报告，候选不等于已标注金标。
- Trace 记录生成、Judge、embedding、队列和 workflow 生命周期，支持按 trace_id 回放、成本估算和结构化首过率统计；成本是 token 估算，usage/历史单价分量未知会标记；提供补偿 replay 和规范化账单比对 CLI，实际金额仍须与供应商账单核对。新增 quality_evaluation 独立于内容入库保存每轮及失败，首过/最终通过率按实际生效阈值和已终结 thread 统计。

## 自用生产的建议运行方式

1. 先用真实配置启动 Compose，确认 `/api/health/ready` 为 ready，尤其确认 checkpointer 不是 MemorySaver 降级。
2. 首批使用 10–50 条/任务，保留人工审核，不直接批量发布。
3. 每批记录模板版本、Prompt/Skill hash、模型、Judge、阈值、RAG 是否命中和成本；异常批次先停生成再排查 Trace。
4. 配置数据库备份，并定期在独立数据库做恢复演练；不能只依赖 Docker volume。
5. 给人工审核保留明确入口，拒绝样本和争议样本进入独立评测集，不要直接用 dashboard 的自动通过率代表题目正确率。

本轮 P0-1 至 P0-5 与 P1 九项代码修复已通过本地回归；在完成 [验证状态与风险](验证状态与风险.md) 中剩余真实人工金标和持久化恢复验收之前，建议把系统定位为“受控内部生产工具”，而不是“质量和可靠性已经证明的生产平台”。
